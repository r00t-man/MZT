# 🛰️ VPN Ops Dashboard — как сделать личную панель для инфраструктуры

Инструкция описывает архитектуру и реализацию приватного веб-сайта для управления
инфраструктурой VPN-сервиса: инвентаризация серверов/провайдеров/доменов, база знаний
(инструкции), живой статус нод, поиск, админка для редактирования контента и панель
внешнего вида. Сайт рассчитан на одного-двух операторов, доступен только через SSH-туннель
на `127.0.0.1`, без публичного интерфейса.

Текст написан так, чтобы его можно было скормить целиком (ссылкой на репозиторий или файлом)
ИИ-агенту в консоли (Claude Code, Cursor, Codex и т.п.) и получить рабочую копию сайта —
описана не только идея, но и конкретные технические решения, которые стоит повторить один в
один, и решения, где можно свободно импровизировать.

> [!NOTE]
> Никаких реальных доменов/IP/токенов/имён в примерах ниже нет — только структура и схемы.

---

## 💡 1. Идея и принципы

Это не сайт для клиентов — это **внутренняя рабочая панель оператора**. Задачи:

- 📇 держать актуальный список серверов/провайдеров/доменов/ботов в одном месте вместо
  разрозненных заметок, таблиц и переписок
- 📚 хранить базу знаний (как что настроено, что делать при типовых проблемах, архитектурные
  решения) в виде обычных markdown-файлов, а не вики стороннего сервиса
- 🩺 показывать не только статичные заметки, но и **живой** статус (нода жива? какая версия
  клиента у пользователей? какие протоколы сейчас проходят?) — с явным fallback на последний
  известный снэпшот, если живой источник недоступен
- 🔍 дать быстрый полнотекстовый поиск по всему этому сразу
- ✍️ дать простую админку для правки без захода на сервер и без git-коммитов на каждую мелочь

> [!IMPORTANT]
> Такой сайт **не** притворяется защищённым мультипользовательским SaaS. Единственная
> реальная граница безопасности — что порт слушает только `127.0.0.1`, и доступ снаружи
> возможен только через SSH-туннель. Всё остальное (логин в админку, маскировка секретов) —
> это защита от чужого взгляда через плечо, а не от целенаправленной атаки. Это осознанное
> решение, а не недосмотр — подробнее в разделе 🔒 [Security model](#-12-security-model).

Ключевая архитектурная идея: **YAML-файлы как база данных**. Каждая "сущность" (сервер,
провайдер, домен, бот, секрет) — один YAML-файл в соответствующей папке `data/`. Без БД, без
ORM, без миграций. Редактируется руками, через git, или через простую админ-форму. Это
осознанное упрощение для проекта с одним-двумя пользователями и сотнями, не миллионами,
записей.

## 🧱 2. Стек технологий

| Слой | Технология |
|---|---|
| Фреймворк | **Next.js 16** (App Router), **React 19**, TypeScript |
| Стили | **Tailwind CSS 4** (CSS-first конфиг через `@theme`, без `tailwind.config.js`) |
| UI-кит | **shadcn/ui** поверх Tailwind 4 (стиль `base-nova`, иконки `lucide-react`) |
| Markdown | **gray-matter** (frontmatter) + **unified/remark/rehype** пайплайн |
| Подсветка кода | **rehype-pretty-code** (Shiki) |
| Диаграммы | **mermaid** — рендер на клиенте после гидратации |
| Поиск | **minisearch** + **cmdk** (command-palette UI, ⌘K) |
| Данные | **yaml** (npm-пакет) — чтение YAML-файлов как данных |

Пайплайн рендера markdown целиком:

```
remark-parse → remark-gfm → remark-directive → (свой плагин колаутов) → remark-rehype
  → (свой плагин mermaid) → rehype-pretty-code (Shiki) → rehype-stringify
```

> [!WARNING]
> **Next.js 16 переименовал `middleware.ts` в `proxy.ts`.** Файл для аутентификации на
> уровне запроса теперь называется `proxy.ts` в корне проекта. Если отдаёте это задание
> ИИ-агенту, обученному на более старых доках Next.js — он по умолчанию попытается написать
> `middleware.ts`, и тот просто не сработает. Стоит явно указать это в промпте (см. раздел
> 14).

## 🧭 4. Меню и навигация

Меню — **статический массив**, а не автогенерация по файлам:

```ts
// components/layout/nav-items.ts
type NavItem = { title: string; href: string; icon: LucideIcon; color: AccentColor };
const navItems: NavItem[] = [
  { title: "Дашборд",  href: "/",              icon: LayoutDashboard, color: "sky" },
  { title: "Серверы",  href: "/servers",       icon: Server,          color: "teal" },
  { title: "Провайдеры", href: "/providers",   icon: Building2,       color: "amber" },
  // ...
];
```

Каждому пункту — свой акцентный цвет, но не через Tailwind-классы (их бы не подхватил
сборщик для динамических значений), а через инлайновую CSS-переменную:
`style={{ "--ac": "var(--color-sky)" }}` + класс типа `text-[var(--ac)]`.

Два взаимозаменяемых рендерера читают один и тот же `navItems`:
- 🖥️ `Sidebar.tsx` — вертикальная панель (десктоп)
- 📱 `HorizontalNav.tsx` — верхняя панель с переносом пунктов по ширине

Какой из них показывать — **не media-query, а настройка** (`settings.layout`), которая
задаётся по умолчанию в `/admin/settings` и может быть переопределена лично на клиенте через
localStorage. Активный пункт подсвечивается через `usePathname()` + `startsWith()` (кроме
корня — там точное совпадение).

Отдельный статический словарь (`INSTRUCTION_CATEGORY_META`) даёт бейджи-категории
(баг/процедура/архитектура/поддержка/исследование) только внутри списка статей — к общей
навигации отношения не имеет.

## 📚 5. База знаний (markdown-статьи)

Файлы — `docs/instructions/*.md`, frontmatter через `gray-matter`:

```yaml
---
title: "Название статьи"
updated: "2026-08-07"
category: procedure   # bug | procedure | architecture | maintenance | research
tags: []               # например "home" — если статья про домашнюю инфраструктуру
helperAccess: false     # видна ли роли "помощник" в админке, не только "админ"
---
```

Рендер (`lib/markdown.ts`) — server component `MarkdownRenderer`, весь HTML собирается на
сервере через unified-пайплайн (см. раздел 2) и вставляется через `dangerouslySetInnerHTML`
(контент полностью свой, доверенный — XSS-риска от собственных markdown-файлов нет).

Два момента, которые проще один раз явно продумать, чем потом чинить:

**1️⃣ Колауты (`:::warning ... :::`)** — через `remark-directive` + собственный небольшой
плагин, который превращает directive-узлы `info/warning/danger/note` в
`<div class="callout callout-warning">`. Готовых remark-плагинов под это несколько, но свой
на 20 строк даёт полный контроль над классами/иконками.

**2️⃣ Mermaid-диаграммы не рендерятся на сервере.** Свой rehype-плагин на HAST-дереве находит
`<pre><code class="language-mermaid">` и заменяет на
`<div class="mermaid-diagram" data-mermaid="...">`. Сам SVG рисуется **в браузере**:
единственный клиентский компонент `MarkdownEnhancements`, смонтированный один раз в
`layout.tsx`, при каждой смене маршрута ищет ещё не отрисованные `.mermaid-diagram`,
динамически импортирует `mermaid`, вызывает `mermaid.render()` и вставляет результат. Тот же
компонент вешает кнопку "Скопировать" на каждый блок кода (обычным DOM API, не через React
state — код-блоки пришли через `dangerouslySetInnerHTML`, React их не "видит"). Это позволяет
держать `MarkdownRenderer` server-компонентом и не тащить mermaid в серверный бандл.

Подсветка синтаксиса — `rehype-pretty-code` (Shiki), фиксированная тема `github-dark`.

## 📇 6. Сущности с YAML-данными (серверы/провайдеры/домены/боты)

Один generic загрузчик на всё:

```ts
// lib/data.ts (упрощённо)
function readYamlDir<T>(dir: string): T[] {
  return fs.readdirSync(path)
    .filter(f => f.endsWith(".yaml") || f.endsWith(".yml"))
    .map(f => YAML.parse(fs.readFileSync(path.join(dir, f), "utf8")))
    .sort((a, b) => a.name.localeCompare(b.name, "ru"));
}
const getServers = cache(() => readYamlDir<Server>("data/servers"));
const getServer = cache((slug: string) => getServers().find(s => s.slug === slug));
```

`cache()` из React — мемоизация в пределах одного запроса (не между запросами, страницы всё
равно `force-dynamic`).

Примерная схема (только форма, не конкретные значения):

```ts
type Server = {
  slug: string; name: string;
  address?: string; ip: string; ipv6?: string; sshPort: number;
  provider: string;        // 🔗 slug провайдера — foreign key
  cdnProvider?: string;     // отдельный провайдер под CDN, если он не совпадает с хостером
  purpose?: string; cost?: string; country?: string; expiresAt?: string;
  os?: string; kernel?: string; cpu?: string; ram?: string; disk?: string;
  configs?: { label: string; path: string }[];   // whitelist путей для скачивания
  notes?: string[];
};

type Provider = {
  slug: string; name: string; url?: string; panelUrl?: string; login?: string;
  hasApi: boolean; apiNote?: string;
  docSlug?: string;   // можно приложить целую markdown-статью с API-документацией
  notes?: string[];
};
```

Аналогично `Domain` (регистратор/DNS/провайдер/сроки) и `BotEntry` (какой сервер, рантайм,
переменные окружения, зависимости — тоже foreign key на сервер и опционально на "область
секретов").

Списки — сетка карточек (`<Card>` из shadcn, обёрнутая в `Link`, свой акцентный цвет тем же
приёмом с `--ac`). Детальная страница — `notFound()` на несуществующий slug, дальше набор
мелких переиспользуемых блоков (`KeyValueRow`, `NotesList`, `ConfigDownloadList`) и
кросс-ссылки на связанные сущности (сервер → его провайдер, провайдер → его сервера и
домены).

> [!TIP]
> **Паттерн "снэпшот + живые данные"**, используемый на страницах серверов, стоит взять за
> общее правило для любых внешних данных:
> ```ts
> const liveHw = await probeHardwareOverSsh(server).catch(() => undefined);
> const liveStatus = await getRemnawaveNodeByAddress(server.remnawaveAddress).catch(() => undefined);
> // в разметке — liveHw?.ram ?? server.ram, и т.п.
> ```
> Живой источник — опциональное улучшение, YAML — надёжный fallback. Страница никогда не
> падает и не показывает пусто, если удалённый сервер/API временно недоступен.

## 🔍 7. Поиск

`lib/search-index.ts` собирает **minisearch-индекс заново на каждый запрос** к
`/api/search` (без кеша) — для сотен записей это доли миллисекунды, а свежесть данных важнее
микрооптимизации. В индекс попадают: все сущности (`servers/providers/domains/bots`), все
статьи `docs/instructions/*.md`, фиксированный список тематических страниц верхнего уровня.
Поле поиска — `title` (вес ×2) + `text` (конкатенация всех текстовых полей записи),
`prefix: true, fuzzy: 0.2`.

UI — `cmdk`-палитра (⌘K/Ctrl+K), debounce 120мс, группировка результатов по разделу,
`router.push()` на выбор.

> [!CAUTION]
> Если в такой индекс попадают чувствительные данные (например, секреты, см. раздел 10) —
> API должен отдавать наружу только `{id, title, section, url}`, никогда исходное поле
> целиком, даже если оно было проиндексировано.

## 🩺 8. Живые/динамические разделы (примеры паттерна)

Кроме страниц серверов, тот же принцип "живой fetch с fallback и таймаутом" стоит применять
везде, где сайт обращается к внешним системам:

- 🟢 статус ноды/панели VPN — прямой fetch к своему API-панели (или тому, что вы используете)
  с `cache: "no-store"`
- 📡 проверка доступности протоколов — отдельный локальный HTTP-сервис (свой чекер),
  опрашивается простым `fetch` с коротким таймаутом (3–5с), без промежуточного `app/api/*`
  роута, если чекер и сайт на одной машине
- 📊 статистика по версиям клиентов — раз в час (`revalidate: 3600`), с делением на
  «актуальная/устаревшая» версия относительно **максимальной увиденной**, а не хардкод
  «последний релиз» — так не нужно поддерживать список версий руками
- ✅ задачи/kanban — если у вас уже есть markdown-файл с задачами в формате GFM-таблиц, не
  надо переносить его в новый формат: распарсить `remark-parse + remark-gfm` напрямую, без
  gray-matter, и превратить строки таблицы в структурированные объекты

> [!NOTE]
> Общее правило: любой внешний вызов — `try/catch` с осмысленным fallback на последний
> известный снэпшот, никогда "страница 500" из-за недоступности одного удалённого сервера.

## 🔐 9. Админка

**Аутентификация** — HTTP-only cookie + гейт на уровне `proxy.ts` (в Next 16 это
переименованный `middleware.ts`, см. раздел 2), матчащий `/admin/:path*` кроме
`/admin/login`.

Токен сессии — не случайный, а **детерминированно выводимый** из данных пользователя:
`sha256(username:passwordHash:статическая-соль)`. Причина: `proxy.ts` в Next.js исполняется
как отдельный изолированный модуль (нет общего in-memory состояния с остальным сервером),
поэтому токен нужно уметь пересчитать одинаково в обоих местах без общей сессионной БД. Смена
пароля автоматически инвалидирует старые сессии, потому что хэш меняется. Для многослойности
каждая admin-страница/server action ещё раз вызывает проверку сессии сама — на случай если
правило матчинга в `proxy.ts` когда-нибудь случайно ослабят.

Пользователи — плоский `data/users.json`, пароли — `scrypt` с индивидуальной солью, две роли
(`admin` / `helper`, где помощнику видны только статьи с `helperAccess: true`). При первом
запуске без файла — создаётся дефолтный пользователь (это осознанно, т.к. сайт не смотрит
наружу — см. раздел 12).

✍️ Редактор статей — **обычная `<textarea>` с тулбаром**, не WYSIWYG: кнопки жирный/курсив/
заголовки/список/цитата/код через ручную склейку строки по `selectionStart`/`selectionEnd`,
без предпросмотра и без загрузки картинок. Это осознанное упрощение — WYSIWYG-редактор
markdown с полной синхронизацией существенно дороже в разработке и не нужен для внутренней
базы знаний на пару авторов.

Остальные разделы админки — по вкусу под свою инфраструктуру: 🎨 настройки внешнего вида по
умолчанию, 👤 управление пользователями, 💰 финансовый учёт (если хотите вести учёт стоимости
серверов помесячно — простой JSON-файл на месяц с суммами и возможностью клонировать прошлый
месяц как основу).

## 🔑 10. Секреты — честно, без иллюзий

Если решите добавить раздел с паролями/токенами:

> [!WARNING]
> Это **не** менеджер секретов и не должно им притворяться. Значения хранятся в открытом
> виде в YAML — так же, как любая другая сущность.

- на странице значение маскируется **только визуально** (фиксированная строка точек, не
  зависящая от реальной длины, чтобы не выдавать длину секрета), разворачивается по клику,
  копируется в буфер отдельной кнопкой
- явно напишите на странице disclaimer, что маскировка — это защита от взгляда через плечо у
  вас за спиной, а не от кого-либо с доступом к самому серверу/файловой системе/логам
- если у вас есть общий поиск (раздел 7) — решите заранее, индексировать ли значения
  секретов вообще. Проще не индексировать поле со значением, оставить поиск только по
  названию/области

Настоящая граница защиты — сетевая (см. раздел 12), не эта страница.

## 🎨 11. Внешний вид: два независимых слоя

**1️⃣ Настройки сайта по умолчанию** — `data/settings.json`, правится только через
`/admin/settings`, рендерится на сервере (без "мигания" дефолтной темой до гидратации).

**2️⃣ Личные настройки посетителя** — тот же формат в `localStorage` браузера, применяются
client-side уже после монтирования, переключаются кнопкой в топбаре и никогда не трогают
файл настроек на сервере. Есть кнопка "сбросить к настройкам сайта".

Палитры — набор именованных пресетов (объекты с hex-значениями под все CSS-переменные
shadcn/Tailwind: background/foreground/card/primary/.../sidebar-*), применяются через прямую
запись в `document.documentElement.style` — то есть переключение темы это не toggle одного
CSS-класса `.dark`, а замена целого набора CSS-переменных поверх него. Если хотите жёстко
тёмный сайт (как в оригинале) — держите `<html class="dark">` всегда, а "светлые" пресеты
делайте просто светлыми по значениям цвета, не завязывайтесь на медиа-запрос
`prefers-color-scheme`.

Анимированные фоны — декларативный реестр (`id`, `label`, `category: css|canvas`,
`settingsSchema` — типизированный список полей для автогенерации формы настроек: цвет,
слайдер с min/max/step). CSS-эффекты — обычные компоненты, canvas-эффекты — отдельные
клиентские компоненты (`"use client"`), выбираются через `switch` по `type` в диспетчере.

## 🔒 12. Security model

> [!IMPORTANT]
> Такой сайт **сознательно не проектируется** как публичный сервис с многоуровневой
> защитой. Модель безопасности одна: **порт слушает только `127.0.0.1`, доступ снаружи —
> исключительно через SSH-туннель** (`ssh -L 4127:127.0.0.1:4127 user@host`). Всё остальное
> (логин в админку, дефолтный пользователь при первом запуске, маскировка секретов) — это
> удобство и защита от случайного взгляда, а не от целенаправленной атаки, и это надо явно
> писать в документации своего форка, чтобы не создавать ложное чувство защищённости у того,
> кто будет это поддерживать после вас.

Если вам всё-таки нужен внешний доступ — не открывайте порт наружу напрямую; поставьте перед
ним отдельный reverse-proxy с нормальной аутентификацией (OAuth/Basic+IP-whitelist/mTLS) и
рассматривайте текущую admin-аутентификацию как вторую, а не единственную линию защиты.

## 🚀 13. Деплой

Без Docker — обычный `next start` под systemd:

```ini
[Unit]
Description=VPN Ops Dashboard
After=network.target

[Service]
Type=simple
WorkingDirectory=/opt/vpn-ops-dashboard
ExecStart=/usr/bin/npx next start -p 4127 -H 127.0.0.1
Restart=always
RestartSec=10
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target
```

> [!WARNING]
> `-H 127.0.0.1` — обязательно, иначе Next по умолчанию слушает все интерфейсы.

Сборка — `npm run build` перед первым стартом и после любых изменений в
`.tsx`/`.css`/зависимостях; правки в `data/*.yaml` и `docs/**/*.md` подхватываются на лету,
пересборка не нужна (страницы `force-dynamic`, читают файлы при каждом запросе).
