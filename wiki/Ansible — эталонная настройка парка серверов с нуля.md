# Ansible — эталонная настройка парка серверов с нуля

Гайд для тех, кто **никогда не работал с Ansible**: с чего начать, куда что класть, что и когда редактировать руками, какими командами запускать. На реальном примере — единый эталон первичной настройки для парка из нескольких VPS (пакеты, SSH-хардненинг, fail2ban, sysctl-тюнинг, unattended-upgrades, мониторинг), но принципы применимы к любому парку серверов, не только VPN.

> [!NOTE]
> Все IP/домены/имена ниже — примеры (`SERVER_IP`, `example.com`, диапазон `203.0.113.0/24` из RFC 5737). Подставляй свои значения.

> [!IMPORTANT]
> Ansible **не ставится на управляемые серверы** — только на один "управляющий" компьютер (твой ноутбук, отдельный VPS-менеджер). С него по SSH накатываются изменения на все остальные. Управляемым серверам вообще ничего специального ставить не нужно, кроме Python3 (обычно уже есть в любом Ubuntu/Debian).

---

## 0) Быстрая логика

1. На управляющей машине ставим `ansible`.
2. Заводим SSH-доступ по ключу на все серверы (сначала по паролю, потом ключ, потом пароль выключаем).
3. Описываем серверы в `inventory` — какие есть и в каких группах.
4. Описываем параметры (`group_vars`/`host_vars`) — что для какой группы/сервера отличается.
5. Пишем **роль** — набор задач ("тасков"), которые нужно выполнить.
6. Собираем **плейбук** — какую роль на какие серверы накатить.
7. Сначала всегда **dry-run** (`--check --diff`) — смотрим, что изменится, ничего не трогая.
8. Только потом реальный прогон.

---

## 1) Установка Ansible на управляющей машине

```bash
sudo apt update
sudo apt install -y ansible
```

Проверка:

```bash
ansible --version
```

Если версия старая (Ubuntu 20.04 и старше) — можно поставить через `pip` в отдельном venv, но для 22.04/24.04 пакета из apt обычно достаточно.

## 2) Первый заход на новый сервер и SSH-ключ

Новый VPS обычно даёт доступ **по паролю root** (или отдельного пользователя). Первое, что нужно сделать — перейти на вход по ключу, чтобы Ansible мог подключаться без пароля.

### 2.1. Сгенерировать ключ (если ещё нет)

На управляющей машине:

```bash
ssh-keygen -t ed25519 -f ~/.ssh/fleet_manager -C "fleet-manager"
```

Появятся два файла: `~/.ssh/fleet_manager` (приватный, никому не показывать) и `~/.ssh/fleet_manager.pub` (публичный, его и раскладываем по серверам).

### 2.2. Первый вход по паролю и установка ключа

```bash
ssh root@SERVER_IP
# вводим пароль, который дал хостер
```

На самом сервере:

```bash
mkdir -p ~/.ssh && chmod 700 ~/.ssh
echo "ssh-ed25519 AAAA...твой_публичный_ключ..." >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
```

Проще — одной командой с управляющей машины, без ручного копипаста (если `ssh-copy-id` доступен):

```bash
ssh-copy-id -i ~/.ssh/fleet_manager.pub root@SERVER_IP
```

### 2.3. Проверить вход по ключу

```bash
ssh -i ~/.ssh/fleet_manager root@SERVER_IP "echo OK"
```

Если `OK` пришёл без запроса пароля — ключ работает, можно отключать пароль (это уже сделает сама Ansible-роль ниже, вручную можно не трогать).

## 3) SSH-конфиг с алиасами

Чтобы не помнить IP/порт/ключ каждого сервера, заведи `~/.ssh/config` на управляющей машине:

```
Host node1
    HostName SERVER_IP_1
    Port 22
    User root
    IdentityFile ~/.ssh/fleet_manager
    StrictHostKeyChecking accept-new
    ConnectTimeout 10

Host node2
    HostName SERVER_IP_2
    Port 22
    User root
    IdentityFile ~/.ssh/fleet_manager
    StrictHostKeyChecking accept-new
    ConnectTimeout 10
```

После этого `ssh node1` работает так же, как `ssh -i ~/.ssh/fleet_manager root@SERVER_IP_1` — и Ansible будет использовать те же алиасы (см. ниже).

## 4) Структура репозитория Ansible

```
fleet-ansible/
├── ansible.cfg                     # где инвентарь, как подключаться
├── inventory/hosts.yml             # список серверов + группы
├── group_vars/
│   └── all.yml                     # переменные для ВСЕХ серверов
├── host_vars/
│   └── node2.yml                   # переменные конкретно для node2 (переопределяют all.yml)
├── base.yml                        # плейбук — точка входа
└── roles/base/
    ├── defaults/main.yml           # дефолты роли "на всякий случай"
    ├── tasks/
    │   ├── main.yml                # что за чем выполняется
    │   ├── packages.yml
    │   ├── ssh_hardening.yml
    │   └── ...
    ├── handlers/main.yml           # что перезапускать при изменениях
    └── templates/                  # файлы-шаблоны (Jinja2, с {{ переменными }})
```

Создать её можно вручную (`mkdir -p`) или командой `ansible-galaxy init roles/base` (сгенерирует пустые папки для роли).

---

## 5) ansible.cfg — где что искать

```ini
[defaults]
inventory = inventory/hosts.yml
remote_user = root
host_key_checking = False
retry_files_enabled = False
stdout_callback = yaml

[ssh_connection]
ssh_args = -F ~/.ssh/config
```

- `inventory` — не указывать `-i` каждый раз в команде.
- `remote_user` — под каким пользователем подключаться (обычно `root` или свой sudo-пользователь).
- `ssh_args = -F ~/.ssh/config` — **важная строка**: заставляет Ansible использовать твой обычный SSH-конфиг вместо того, чтобы дублировать IP/порт/ключ в инвентаре отдельно. Алиас `node1` в Ansible — это тот же `node1`, что и в `ssh node1` руками.

---

## 6) inventory/hosts.yml — какие серверы и где

```yaml
all:
  children:
    web_nodes:
      hosts:
        node1: {}
        node2: {}
    db_nodes:
      hosts:
        node3: {}
  vars:
    ansible_python_interpreter: /usr/bin/python3
```

Группы — не формальность, а способ применять разные настройки к разным типам серверов (например, у `web_nodes` один набор пакетов, у `db_nodes` — другой). Один сервер может входить в несколько групп.

---

## 7) group_vars и host_vars — что и когда переопределять

`group_vars/all.yml` — общий эталон для всех серверов:

```yaml
base_packages:
  - curl
  - wget
  - htop
  - jq
  - fail2ban

swap_size_mb: 512
timezone: UTC
```

Если для ОДНОГО сервера что-то отличается (например, ему нужно больше свопа) — не трогай `all.yml`, а создай `host_vars/node2.yml`:

```yaml
swap_size_mb: 2048   # у node2 больше RAM, своп побольше
```

**Порядок приоритета** (от низкого к высокому): `roles/*/defaults` → `group_vars/all` → `group_vars/<группа>` → `host_vars/<сервер>`. Более специфичное всегда побеждает более общее.

> [!TIP]
> Если один параметр разъезжается между серверами не просто "иногда", а системно (например, "старый добавляемый сервер vs новый") — заведи отдельную группу в inventory (`group_vars/legacy_nodes.yml`), а не городи `host_vars` на каждый сервер по отдельности.

## 8) Роль — из чего состоит

Роль — это папка `roles/<имя>/` с подпапками. Ansible сам знает, что искать в `tasks/main.yml`, `handlers/main.yml` и т.д. — не нужно ничего явно подключать.

### tasks/main.yml — оркестрация

```yaml
---
- name: Пакеты
  ansible.builtin.import_tasks: packages.yml
  tags: [packages]

- name: SSH-хардненинг
  ansible.builtin.import_tasks: ssh_hardening.yml
  tags: [ssh]
```

`tags` — позволяют накатить только один кусок роли (`--tags ssh`), не гоняя всё остальное.

### tasks/packages.yml — что реально делает работа

```yaml
---
- name: Обновить apt-кэш
  ansible.builtin.apt:
    update_cache: true
    cache_valid_time: 3600

- name: Базовый набор пакетов
  ansible.builtin.apt:
    name: "{{ base_packages }}"
    state: present
```

`state: present` — "пусть будет установлено", не "поставь заново, если уже есть". Это и есть **идемпотентность**: повторный запуск ничего не ломает, просто ничего не меняет, если всё уже так, как надо.

### tasks/ssh_hardening.yml — пример с шаблонной строкой и защитой от опечатки в конфиге

```yaml
---
- name: Выключить вход по паролю, разрешить только ключ
  ansible.builtin.lineinfile:
    path: /etc/ssh/sshd_config.d/00-hardening.conf
    create: true
    mode: "0644"
    line: "{{ item }}"
    regexp: "^{{ item.split()[0] }} "
    validate: "sshd -t -f %s"
  loop:
    - "PasswordAuthentication no"
    - "PermitRootLogin without-password"
    - "PubkeyAuthentication yes"
  notify: restart sshd
```

`validate: "sshd -t -f %s"` — перед тем как реально записать файл, Ansible прогоняет проверку синтаксиса. Если конфиг битый — файл не запишется и SSH не перезапустится, ты не запрёшь себе доступ.

`notify: restart sshd` — не перезапускает SSH сразу, а "звонит" в хендлер (см. ниже) в конце всего прогона, и только если что-то реально поменялось.

### handlers/main.yml — что перезапускать

```yaml
---
- name: restart sshd
  ansible.builtin.systemd:
    name: ssh
    state: restarted
  when: not ansible_check_mode
```

`when: not ansible_check_mode` — **важная деталь**, без неё словишь ошибку в dry-run (см. раздел 11 ниже).

### templates/ — файлы с подстановкой переменных (Jinja2)

`templates/99-tuning.conf.j2`:

```ini
# профиль: {{ tuning_profile }}
net.core.somaxconn = {{ 8192 if tuning_profile == 'big' else 4096 }}
```

Таск, который его разворачивает:

```yaml
- name: Развернуть sysctl-тюнинг
  ansible.builtin.template:
    src: 99-tuning.conf.j2
    dest: /etc/sysctl.d/99-tuning.conf
    mode: "0644"
  notify: reload sysctl
```

Разница `copy` vs `template`: `copy` копирует файл один в один, `template` — прогоняет через Jinja2 и подставляет `{{ переменные }}` под конкретный сервер/группу.

## 9) Плейбук — точка входа

`base.yml` в корне репозитория:

```yaml
---
- name: Base setup — эталонная настройка парка
  hosts: web_nodes:db_nodes
  become: false
  serial: 3
  roles:
    - base
```

- `hosts:` — на каких группах/серверах выполнять (можно перечислить через `:`).
- `become: false` — уже подключаемся под root (или под sudo-пользователем с `become: true`, если так у тебя настроено).
- `serial: 3` — **важно для парка из многих серверов**: применять изменения волнами по 3 сервера, а не на всех разом. Если что-то пойдёт не так — сломаются максимум 3, а не весь парк, и можно остановиться и починить.

## 10) Как запускать

### Проверить синтаксис (ничего не подключает)

```bash
cd fleet-ansible
ansible-playbook base.yml --syntax-check
```

### Dry-run — обязательно перед первым реальным прогоном

```bash
ansible-playbook base.yml --check --diff --limit node1
```

`--check` — ничего не меняет на сервере, только показывает, что бы изменилось. `--diff` — показывает конкретные построчные различия файлов. `--limit node1` — только один сервер (для проверки перед раскаткой на всех).

### Реальный прогон

```bash
ansible-playbook base.yml --limit node1       # один сервер
ansible-playbook base.yml                      # весь inventory, волнами (serial)
```

### Только часть роли

```bash
ansible-playbook base.yml --tags ssh
```

## 11) Частые грабли dry-run (`--check`) — прочитать перед первым запуском

Это не баги Ansible, а особенность режима `--check` — модули `command`/`shell` по умолчанию **вообще не выполняются** в dry-run (слишком рискованно угадывать, безопасны ли произвольные команды). Из-за этого можно словить обманчивые ошибки именно в `--check`, которых не будет в реальном прогоне.

### 11.1. Read-only команда молча пропускается

```yaml
- name: Узнать текущую версию пакета
  ansible.builtin.command: mytool --version
  register: _version
  changed_when: false
```

В `--check` этот таск **пропускается**, `_version` остаётся пустым — если дальше по нему есть `when:`-условие, оно может сработать неправильно. Чинится добавлением `check_mode: false` (заставляет таск выполниться по-настоящему, даже в dry-run — безопасно для read-only команд):

```yaml
  changed_when: false
  check_mode: false
```

### 11.2. Цепочка зависимых шагов ломается в dry-run

Если шаг 2 работает с файлом, который "создаёт" шаг 1 — в `--check` шаг 1 только СИМУЛИРУЕТ создание (реально файла нет), и шаг 2 упадёт с "файл не найден". Решение — не пытаться честно просимулировать всю цепочку, а просто пропустить зависимые шаги в dry-run:

```yaml
- name: Создать файл (в --check только покажет "changed")
  ansible.builtin.command: some-tool --create /path/to/file
  args:
    creates: /path/to/file

- name: Что-то сделать с уже созданным файлом
  ansible.builtin.file:
    path: /path/to/file
    mode: "0600"
  when: not ansible_check_mode
```

### 11.3. Хендлеры не проверяют check-mode сами по себе

Если хендлер (`restart myservice`) вызван таском, который **тоже** только симулировался (например, `apt: state=present` пакета, который ещё не стоит на свежем сервере) — хендлер попытается перезапустить сервис, которого физически ещё нет, и упадёт с `Could not find the requested service`. Добавляй `when: not ansible_check_mode` в каждый хендлер, который может сработать на "ещё не установленном" сервисе:

```yaml
- name: restart myservice
  ansible.builtin.systemd:
    name: myservice
    state: restarted
  when: not ansible_check_mode
```

> [!TIP]
> Проверять это стоит именно на **по-настоящему пустом** новом сервере, а не на уже настроенном — на уже настроенном сервере эти грабли просто не проявятся (пакет/сервис уже есть, dry-run это не пересоздаёт).

## 12) firewall/fail2ban + новые сервисы — проверить порты заранее

Если роль ставит защиту от сканирования портов (fail2ban с "ловушкой" на редкие порты вроде 3306/6379/27017 и т.п.) — а следующим шагом (другим плейбуком/ролью) на сервере поднимается реальный сервис именно на одном из "ловушечных" портов — получится, что легитимный трафик к своему же сервису будет трактоваться как сканирование и банить сам себя (вплоть до полной блокировки SSH, если бан настроен "на все порты").

**Правило:** перед раскаткой такой защиты — сверить реально занятые/планируемые порты (`ss -tlnp`) со списком "ловушечных", и **после** каждого нового сервиса, который слушает новый порт — перепроверять список ещё раз, а не полагаться, что сверка была сделана один раз в начале.

Если всё же забанил сам себя: бан обычно привязан к конкретному IP-адресу, с которого шло "подозрительное" подключение. Если есть доступ ещё к одному серверу с ДРУГИМ исходящим IP — можно зайти в обход, прыгнув через него:

```bash
ssh -J другой_сервер root@SERVER_IP
```
(`-J` = ProxyJump, подключение "прыжком" через промежуточный хост — трафик до целевого сервера пойдёт с IP промежуточного, не забаненного).

---

## 13) Добавление нового сервера — весь путь

1. Первый вход по паролю, ключ добавлен (раздел 2).
2. Алиас в `~/.ssh/config` (раздел 3).
3. Строка в `inventory/hosts.yml`, в нужную группу.
4. Если параметры отличаются от `group_vars/all.yml` — `host_vars/<алиас>.yml`.
5. `ansible-playbook base.yml --check --diff --limit <алиас>` — посмотреть diff.
6. Если всё ожидаемо — `ansible-playbook base.yml --limit <алиас>` без `--check`.
7. Проверить живьём: зайти по SSH, убедиться что сервисы подняты (`systemctl status ...`).
