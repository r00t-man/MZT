
# 🛡️ Архитектура VPN для минимизации детектов и слежки 📱

## Введение
### 🚨 Главный вывод из отчёта
**Основная поверхность детекта** в отчёте — это **клиентская сторона Android**. Большинство приложений не детектируют "подозрительный VPN-сервер", а скорее **выявляют факт наличия VPN на устройстве**. Это может быть **сигналом** для приложений, которые используют **интерфейс `TRANSPORT_VPN`**, проверку сетевого интерфейса `tun0`, или обращение к **списку установленных приложений**.

**Этот документ поможет вам построить архитектуру VPN** для минимизации детектов и повышению безопасности ваших устройств, особенно при работе с российскими приложениями.

---

## Общий принцип

### 🎯 Цель:
**Изолировать VPN-трафик** и скрыть наличие VPN-приложений на устройстве, чтобы избежать детектов, как описано в отчёте. Все методы минимизации детектов основаны на изоляции и разделении трафика и приложений.

---

## Архитектура VPN

### 🔑 **Слой 1: Edge-входы**

#### 🌐 **Вход 1: VPN-шлюз на роутере**


Телефон -> Wi-Fi (с VPN-шлюзом) -> Внешний VPN-сервер

Используйте роутер с поддержкой VPN (например, OpenWrt, Mikrotik, Keenetic).

VPN-туннель начинается на роутере, все устройства подключаются через Wi-Fi.

Преимущества: VPN скрыт на роутере, а российские приложения не видят VPN на телефоне.


📱 Вход 2: Телефон с VPN и раздачей Wi-Fi

Телефон A (с VPN) -> Wi-Fi -> Телефон B (с российскими приложениями)

Телефон A с активированным VPN раздаёт Wi-Fi.

Телефон B подключается через этот Wi-Fi.

Преимущества: VPN остаётся скрытым на основном устройстве, а российские приложения не видят VPN.


📲 Вход 3: Второй телефон, только для российских приложений

Телефон A (с VPN) -> Wi-Fi -> Телефон B (только российские приложения)

Телефон A используется для VPN-сервисов.

Телефон B используется исключительно для работы с российскими приложениями.

Преимущества: Сегрегация трафика, российские приложения не видят VPN.



---

🚀 Слой 2: Transport Pool

Используйте разные транспортные протоколы (например, TLS на порту 443, WebSocket, xHTTP) для повышения устойчивости к блокировкам.

Основной порт должен быть стандартным — 443. Это минимизирует риски при анализе трафика.

Выходы через одни и те же IP-адреса должны быть стабильными, чтобы избежать частых переключений географических локаций.



---

🌍 Слой 3: Политики маршрутизации

Трафик -> VPN / Чувствительные сервисы / Российские сервисы / Зарубежные сервисы

Разделите трафик по категориям:

Обычный трафик — через VPN.

Чувствительные сервисы — через отдельные туннели.

Российские сервисы — доступ через VPN, с учётом защиты от детектов (например, через DNS-сервер с локальным разрешением).

Зарубежные сервисы — полный доступ через VPN.




---

🛑 Слой 4: Пользовательские рекомендации

🛡️ Ограничения разрешений

Геолокация: Отозвать разрешение для всех российских приложений, кроме навигаторов.

Контакты: Отозвать для всех приложений, кроме мессенджеров.

Микрофон и камера: Предоставлять только по запросу.

Журнал звонков и SMS: Отозвать для всех приложений.


⚡ Ограничение фоновой активности

Для всех приложений, работающих в фоне, используйте настройки оптимизации батареи:

Settings → Battery → "Limited"




---

🔒 Слой 5: Безопасность через изоляцию

Android Work Profile (через Shelter) для разделения российских приложений от обычных VPN-программ.

Важно: Work Profile не скрывает факт работы VPN, но позволяет изолировать данные между профилями.



---

Резюме

1. Основной VPN: На роутере или через второй телефон, который раздаёт Wi-Fi.


2. Разделение приложений: Российские приложения на отдельном устройстве или в Work Profile.


3. Не использовать один телефон для всего: Лучше два устройства для работы с VPN и для использования российских приложений.


4. Поддержка стабильного egress: Для стабильности выходных данных используйте постоянные выходы через один ASN или IP.




---

Улучшения для минимизации детектов

💡 1) Перенести VPN с устройства на внешний шлюз

VPN на роутере или отдельном устройстве минимизирует риски детекций, так как нет активного VpnService и tun0 на Android.

Гораздо более надёжно, чем на мобильном устройстве.


🔌 2) Разделение устройств/профилей

Телефон с российскими приложениями не должен быть VPN-клиентом.

Используйте второй телефон для VPN или специальный Work Profile для изоляции трафика.


🔧 3) Снижение палевности клиентского поведения

Уменьшение использования proxy-настроек и нестандартных переключений между туннелями.

Трафик должен выглядеть как стандартный HTTPS-трафик с минимальными отличиями.



---

Что стоит переоценить

Не все серверные маскировки решат проблему на клиентской стороне. Вот что в отчёте не даёт эффекта:

🚫 1. Маскировка через TLS, SNI, 443

Это помогает против DPI и фильтрации, но не решает проблему Android API-детекта.


🚶 2. Split tunneling как "решение"

Частично помогает, но не прячет tun0.


🔒 3. Work Profile как панацея

Изолирует данные между профилями, но не скрывает факт работы VPN.



---

Пример оптимальной архитектуры

Лучший вариант

RU-приложения → отдельный телефон / отдельный Android-профиль → подключение через внешний Wi-Fi-шлюз → твой VPN edge → магистраль / каскад / нужный выход

Что это даёт:

RU-приложение не видит локальный VPN-клиент.

Не видит tun0 на своём устройстве.

Не видит VPN-приложение в списке установленных.


Хороший компромисс

Телефон A с VPN → раздаёт Wi-Fi → телефон B с RU-приложениями работает через этот Wi-Fi

Преимущества:

Работает, но с оговорками по tethering на Android 12+.


Слабый вариант

Один Android, VPN-клиент прямо на нём → внешний VPN сервер

Не лучший выбор, так как Android-приложения могут легко детектировать VPN.


---

Заключение

🔑 Самое эффективное улучшение для минимизации детектов — это перенести VPN с устройства на внешний шлюз. Проблема детектов в отчёте кроется в клиентской стороне, и сервера не смогут скрыть многие из этих признаков.


---

Примечания:

1. Использование двух телефонов или Work Profile помогает избежать многих детектов на клиентской стороне.


2. Важно помнить, что маскировка транспортного уровня не решает все проблемы с детекцией, особенно если VPN работает на том же устройстве с российскими приложениями.



Часто архитектура клиента важнее архитектуры сервера!
