# 📶 LTE Base Station Bypass — обход мобильного DPI через платный CDN-гейтвей хостера

[![OS Linux](https://img.shields.io/badge/OS-Linux-blue?logo=linux&logoColor=white)](https://www.linux.org/)
[![Remnawave](https://img.shields.io/badge/Remnawave-panel%20%2B%20nodes-teal?logo=v2ray)](https://github.com/remnawave)
[![License](https://img.shields.io/badge/License-MIT-purple)](../LICENSE)

У некоторых зарубежных VPS-хостеров с готовыми Remnawave/Xray-нодами есть платная допуслуга —
условно назовём её **«Обход базовой станции» (VPN over BS bypass, «LTE bypass»)**. Это не ещё один
протокол на той же ноде, а отдельный CDN-гейтвей, специально откалиброванный именно под путь трафика
мобильного оператора (сотовая БС → DPI оператора → интернет), а не под обычный домашний/датацентровый
интернет.

Статья — как это настроено и эксплуатируется на практике, с граблями, в которые реально влетели за
месяц использования. **Все домены/слаги/UUID ниже — плейсхолдеры**, у твоего хостера/аккаунта будут
свои.

---

## 🧭 Что это физически

- Обычная VPS-нода у хостера (например, уже развёрнутая под Remnawave — IP/порт как у любой другой
  ноды в парке).
- Плюс отдельно оплаченная функция гейтвея — хостер выдаёт **CDN-эндпоинт** вида
  `bs1xxx` (условный «slug» покупки), который проксирует трафик через собственную инфраструктуру
  (в нашем случае — построенную поверх стороннего GSLB CDN, домены менялись, реальная топология
  провайдера, не наша).
- У этого гейтвея **свой домен**, который используется как `address`/`sni`/`host` в Remnawave-Host —
  и этот домен хостер **периодически меняет без предупреждения** (см. раздел про ротацию ниже).

> [!IMPORTANT]
> Это НЕ обычный CDN/WS-инбаунд «через nginx на своём IP», как в [nginx+xhttp+tls+warp](./nginx+xhttp+tls+warp.md).
> Здесь фронт — чужая инфраструктура хостера, и именно поэтому у неё специфичное поведение,
> описанное ниже (ложные срабатывания мониторинга и т.п.).

## 1️⃣ Настройка в Remnawave

### Config Profile + Node

Обычная нода добавляется как всегда (см. [VPN-help-remna-full](./VPN-help-remna-full.md)), только
с 4 инбаундами вместо привычных 5 — под этот гейтвей заводится отдельный `CDN`-тег, `Hysteria2`
обычно не имеет смысла (гейтвей — TCP/TLS-проксирование, не UDP):

```text
tag: xxx-reality
tag: xxx-xhttp
tag: xxx-cdn      ← этот и есть гейтвей хостера
tag: xxx-ws
```

**Грабли #1 — Remnawave требует уникальный `address` для ноды.** Если этот сервер физически на
том же хосте/IP, что и другая уже добавленная нода (частая ситуация — хостер даёт несколько
арендованных «слотов» на одной машине, разные порты) — `POST /nodes` упадёт с ошибкой вида
`node address already exists`. Обход: использовать **hostname**, который резолвится в тот же IP,
вместо голого IP (у хостера обычно есть SFTP/служебный домен вида `nodeX.provider.net` — он подходит).

### Host-запись для CDN-тега

Ключевое отличие от «обычного» XHTTP/CDN-инбаунда на своём IP:

| Поле | Обычный CDN-инбаунд (свой IP) | LTE-гейтвей хостера |
|---|---|---|
| `address`/`sni`/`host` | IP или свой домен ноды | **домен гейтвея хостера** (меняется хостером) |
| `path` | свой, произвольный | **строго тот, что выдал хостер** (обычно вида `/api/v1/bs1xxx/sync/`) |
| `xhttpExtraParams` | обычно `mode: auto` | **весь блок — как прислал хостер, включая `mode: packet-up`** |

> [!WARNING]
> Флот-вайд фиксы бага `xhttpSettings.mode: packet-up` (если он у тебя где-то был, см. типовые
> инбаунды в этом репозитории) **не должны трогать тег этого гейтвея** — здесь `packet-up` не баг,
> а обязательное требование конкретно этого прокси. Если погонишь общий скрипт-фикс по всем
> `config-profiles` — сначала исключи этот тег из выборки.

## 2️⃣ «Плавающий» домен гейтвея

Домен фронта живёт недолго (у нас за месяц эксплуатации сменился больше 10 раз) — хостер обновляет
инфраструктуру гейтвея на своей стороне без предупреждения, старый домен либо перестаёт резолвиться
(`NXDOMAIN`), либо TLS-сертификат на нём внезапно оказывается выпущен на **чужого** клиента той же
облачной CDN-инфраструктуры (реальный симптом, который у нас встречался несколько раз).

### Как обновляется

1. Хостер меняет гейтвей на своей стороне → старый домен дохнет.
2. В личном (клиентском, НЕ панельном) кабинете хостера у сервера обычно есть кнопка вида
   **«Создать новый конфиг» / «Пересоздать доступ»** — жмём, получаем свежий текстовый конфиг с
   новым доменом гейтвея. У части хостеров это можно вытащить и через клиентский REST API (Bearer
   API-ключ из браузерной сессии), но саму кнопку «пересоздать» из API часто **нельзя дёрнуть
   программно** — только руками в веб-панели (проверено: соответствующий API-метод либо
   `405`/`Method Not Allowed`, либо документация прямо ограничивает его другим типом серверов).
3. Из нового конфига меняется **только клиентская Host-запись** в Remnawave (`address`/`sni`/`host`)
   — сам серверный инбаунд (порт, `mode: packet-up`, весь `xhttpExtraParams`) в норме остаётся
   идентичным между ротациями. Проверяй `diff` с прошлым эталоном перед применением, не перезаписывай
   вслепую.

```bash
# быстрая диагностика "домен гейтвея жив или уже дохлый"
openssl s_client -connect <текущий_домен_гейтвея>:443 -servername <текущий_домен_гейтвея> </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer

# если CN сертификата НЕ совпадает с доменом гейтвея (например, вылезает чужой *.cdn-vendor.net) —
# домен реально мёртв, нужна новая ротация, а не диагностика своей ноды
```

### PATCH одним запросом

```bash
curl -sX PATCH "https://panel.example.com/api/hosts" \
  -H "Authorization: Bearer $REMNAWAVE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "uuid": "<host-uuid>",
    "address": "<новый-домен>",
    "sni": "<новый-домен>",
    "host": "<новый-домен>"
  }'
```

## 3️⃣ ⚠️ Главная ловушка — ложный «offline» в любом автомониторинге

Это самая дорогая по времени находка. Гейтвей физически рассчитан на путь трафика **через мобильную
БС оператора** — а не через обычный интернет-канал. Из-за этого:

- Проверка с **датацентрового IP** (сама нода, любой соседний VPS) — таймаут/`400`.
- Проверка с **домашнего резидентского, но НЕ мобильного** IP (обычный проводной/Wi-Fi ISP) — тоже
  фейл.
- Готовые Xray-uptime-чекеры (`xray-checker` и подобные) — показывают `offline`.
- Сторонние Telegram-боты для проверки прокси (даже с реальными мобильными модемами на борту) —
  тоже иногда репортят `0 из N операторов`.

**Во всех перечисленных случаях сервис при этом реально работал** — подтверждено многократно на
живом мобильном устройстве клиента на сотовой сети в момент, когда автоматические проверки кричали
"всё упало".

> [!TIP]
> Единственная надёжная проверка для инбаунда с таким гейтвеем — **реальное мобильное устройство
> на сотовой сети оператора**, не датацентр/домашний Wi-Fi/автоматический чекер. При жалобе «обход
> не работает» — сначала чек-лист (баланс/статус сервера у хостера → статус ноды в Remnawave
> `isConnected`/`xrayUptime` → `openssl s_client` на текущий домен гейтвея, см. выше), и только если
> ВСЁ красное — тогда уже трогать рестарты. Обычно оказывается, что всё зелёное, а «не работает» —
> это ложный результат теста не с той сети.

## 4️⃣ Автоматизация ротации (что мы в итоге сделали)

Руками обновлять Host при каждой ротации домена — не вариант (несколько раз в неделю). Собрали
простой цикл (Python, обычный systemd-таймер/цикл в существующем боте, ничего экзотического):

1. **Раз в N минут** — тянем текущий конфиг гейтвея через клиентский API хостера (если есть) и
   сравниваем домен внутри с тем, что сейчас стоит в Remnawave Host.
2. Если домен отличается — сначала TLS-проверка нового домена (см. `openssl s_client` выше,
   в скрипте — просто `requests.get`, любой ответ = ОК), и только если TLS проходит —
   `PATCH /api/hosts`.
3. **Проактивная проверка (важное дополнение).** Не дожидаться, пока домен реально сменится в
   API — сразу проверять `socket.gethostbyname()` на ТЕКУЩИЙ домен. Если внезапно `NXDOMAIN` —
   значит домен уже умер, а API хостера ещё не в курсе (провайдер обновляет данные не мгновенно).
4. **Если у хостера кнопка «Создать новый конфиг» не вызывается через API** — единственный
   работающий обходной путь: headless-браузер (Playwright), эмулирующий реальный клик человека
   в клиентской панели хостера. Логин по CSS-селекторам (`input[placeholder="..."]`, если у формы
   нет нормальных `name`/`id` атрибутов — так тоже бывает), клик по кнопке, и **отдельно** —
   обработка кастомного JS-модального окна подтверждения (`page.on("dialog", ...)` его НЕ ловит,
   если это не нативный `window.confirm()`, а свой div — нужно искать и кликать кнопку модалки
   явно).
5. Уведомление админу + (опционально) авто-пост в канал для клиентов о ротации — **без слова
   «починено»**, честно «домен обновлён, кто на этом обходе — подтвердите работу с мобильной сети»
   (см. пункт 3 выше про ложные offline — не стоит звучать увереннее, чем позволяет метод проверки).

```python
import socket

def domain_resolves(domain: str) -> bool:
    try:
        socket.gethostbyname(domain)
        return True
    except socket.gaierror:
        return False

# псевдокод главного цикла
def check_rotation():
    if not domain_resolves(current_host_address):
        # домен уже мёртв, провайдер мог ещё не обновить свой API
        if autoclick_enabled:
            click_new_config_button()   # Playwright, см. пункт 4
        else:
            notify_admin("Домен гейтвея мёртв, нужно вручную нажать 'Создать новый конфиг'")
        return

    new_domain = extract_domain(fetch_provider_config())
    if new_domain != current_host_address:
        if tls_ok(new_domain):
            patch_remnawave_host(new_domain)
            notify_admin(f"Домен гейтвея обновлён: {new_domain}")
        else:
            notify_admin(f"Новый домен {new_domain} не прошёл TLS-проверку — не применено")
```

> [!WARNING]
> Если у хостера доступен **отдельный** endpoint «пересоздать ключи» (не тот же самый, что
> «обновить домен гейтвея» — у нас это были два разных действия) — он может **мгновенно и
> необратимо** перевыпустить REALITY private key/shortId на своей стороне. Если такое есть —
> НИКОГДА не применяй ответ такого endpoint'а в Remnawave целиком: полный ответ обычно содержит
> generic-теги/плейсхолдеры (не совпадают с твоими реальными тегами инбаундов), слепой `PATCH`
> им сломает привязку существующих Host-записей к `configProfileInboundUuid`. Бери из ответа
> только то поле, что реально нужно (например, только новый `privateKey`+`shortIds` для тега
> REALITY), и применяй точечно.

## 5️⃣ Минимальный чек-лист диагностики (в таком порядке, не наоборот)

1. Статус сервера/услуги у хостера (активна, оплачена, есть ли ошибка настройки в личном кабинете).
2. Статус ноды в Remnawave: `isConnected`, `xrayUptime` (короткий `xrayUptime` сам по себе — НЕ
   повод для тревоги, ноды рутинно перезапускаются по десятку безобидных причин).
3. `openssl s_client` на текущий домен гейтвея — совпадает ли `CN` сертификата с ожидаемым доменом.
4. Домен из API хостера совпадает с тем, что сейчас в Remnawave Host? Если нет — это и есть
   ротация, нужен `PATCH`.
5. Только если 1-4 все красные — тогда уже рестарт ядра/ноды. Если все зелёные, а жалоба всё ещё
   есть — проси клиента проверить именно **с мобильной сети**, не полагайся на автотест.
