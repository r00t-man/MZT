# Ваше первое изменение: от запроса до коммита

<sub>**Начинающий** · Урок 3 из 5 · около 20 минут · Требуется: [Режимы разрешений и режим плана](02-permission-modes-and-plan-mode.md) · Проверено на Claude Code v2.1.292 (stable) 2026-10-15</sub>

## Цель

К концу этого урока вы сможете провести одно изменение от запроса до коммита: исследовать, спланировать, реализовать, протестировать, просмотреть diff, исправить и закоммитить.

## Вам понадобится

- Ваша копия практического шаблона и Node.js LTS (в Codespace на вашей копии он есть).
- Чтобы практиковаться в одном из ваших собственных репозиториев, сохраните также копию шаблона: проверка выполняется из неё. Настройте папку `.practice/` репозитория, как описано в [уроке 1](01-install-and-look-around.md#you-need), если ещё не сделали этого.
- Отсутствие незакоммиченных изменений там, где вы практикуетесь. Если изменение из урока 2 всё ещё там, отложите его с помощью `git stash push --include-untracked -m b-2`; в своём репозитории вместо этого закоммитьте его, если хотите сохранить. Последующие уроки не используют то, что вы отложили, а `git stash list` покажет это.
- Использование: лёгкое.

## Идея

Просить об изменении и принимать всё, что приходит в ответ, — так сессии идут неправильно. [Лучшие практики](https://code.claude.com/docs/en/best-practices#explore-first-then-plan-then-code) Anthropic рекомендуют четыре фазы: исследование, планирование, реализация и коммит. Этот урок добавляет проверку на каждом шаге:

1. **Исследуйте** в режиме плана: Claude читает и отвечает, ничего не меняя.
2. **Планируйте** и одобряйте план только тогда, когда он соответствует тому, что вы хотите.
3. **Реализуйте**, одобряя правки по мере их появления.
4. **Тестируйте**: именно тесты говорят, что изменение работает, а не резюме, которое пишет Claude.
5. **Просматривайте diff** построчно.
6. **Исправляйте** всё, что вам не нравится, простыми словами.
7. **Коммитьте**, чтобы изменение было сохранено и его легко было отменить.

## Разобранный пример

Практическое приложение проверяет ссылки Markdown, но пропускает любую ссылку с заголовком, например `[setup](setup.md "Setup guide")`. Вы это исправите.

1. Запустите `claude` в своей практической копии и нажимайте `Shift+Tab`, пока в строке состояния не появится `⏸ plan mode on`. Исследуйте:

   ```text
   Как это приложение находит ссылки в файле Markdown? Какие виды ссылок оно пропустит?
   ```

   Ваша формулировка может отличаться, но Claude должен указать на `src/links.js` и упомянуть ссылки с заголовком.
2. Планируйте:

   ```text
   Спланируйте изменение, чтобы ссылки с заголовком, например [setup](setup.md "Setup guide"), тоже проверялись. Добавьте тест для этого в test/links.test.js.
   ```

   Прочитайте план. Когда в нём указаны только `src/links.js` и `test/links.test.js`, выберите **Yes, manually approve edits**. Если он называет и другие файлы, отправьте его обратно, как в [уроке 2](02-permission-modes-and-plan-mode.md#worked-example): в **Tell Claude what to change** попросите Claude ограничить изменение этими двумя файлами.
3. Реализуйте и тестируйте. Одобряйте каждую правку. Claude также спрашивает перед большинством команд, например перед запуском тестов: читайте каждую. Отвечайте просто **Yes**, когда команда делает то, что нужно по плану, как в уроке 2. Отвечайте **No** и говорите, что сделать вместо этого, когда команда делает больше, например команда, которая прячет, перезаписывает или перемещает файлы. Не выбирайте **Yes, and switch to auto mode**: тогда фоновые проверки безопасности будут проверять остальные шаги этого урока вместо вас ([Выбор режима разрешений](https://code.claude.com/docs/en/permission-modes#switch-permission-modes)). Затем спросите, даже если Claude уже запускал тесты, чтобы самим увидеть результат:

   ```text
   запустите тесты
   ```

   Claude Code сворачивает длинный вывод команды в краткое резюме. Нажмите `Ctrl+O`, чтобы развернуть его ([Интерактивный режим](https://code.claude.com/docs/en/interactive-mode#general-controls)), найдите сводку тестов ближе к концу и нажмите `Esc`, чтобы вернуться. Должно быть `fail 0`.
4. Просмотрите diff. Введите `/diff`, чтобы увидеть изменения, сделанные Claude, рядом с любыми другими незакоммиченными изменениями ([Интерактивный режим](https://code.claude.com/docs/en/interactive-mode#review-changes-with-%2Fdiff)). Откроется один из двух видов:
   - Панель рядом с беседой. Её список не показывает тестовые файлы, пока вы не нажмёте строку, которая их подсчитывает, так что нажмите её. Эта строка считает тестовые и сгенерированные файлы вместе, например `1 test/generated (show)`. Панель также может открыться сама, как только Claude отредактирует файлы: если она уже открыта, читайте там, потому что ввод `/diff` закрывает её.
   - Список над строкой ввода. Выберите файл клавишами со стрелками, нажмите `Enter`, чтобы прочитать его diff, и нажмите `Esc`, чтобы вернуться.

   Читайте каждую строку, включая тест. Во втором терминале `git diff` выводит незакоммиченные изменения в файлах, которые git уже отслеживает. Для нового файла, созданного Claude, сначала выполните `git add -N <file>`, чтобы он отобразился ([git add](https://git-scm.com/docs/git-add#Documentation/git-add.txt--N)). Если diff заполняет экран и останавливается на приглашении `:`, git показывает его в пейджере, обычно `less`: нажмите `q`, чтобы выйти ([git config](https://git-scm.com/docs/git-config#Documentation/git-config.txt-corepager), [less FAQ](https://www.greenwoodsoftware.com/less/faq.html#dashe)).
5. Исправляйте. Прочитайте новый тест. Если он покрывает только заголовки в двойных кавычках, спросите:

   ```text
   Тест покрывает только заголовки в двойных кавычках. Добавьте случай для заголовка в одинарных кавычках, например [faq](faq.md 'FAQ'), и снова запустите тесты.
   ```

   Если он уже покрывает одинарные кавычки, попросите другое небольшое изменение, которое вы хотели бы, например отдельный тест для каждого вида заголовка. Затем снова проверьте diff.
6. Коммитьте:

   ```text
   закоммитьте это с сообщением, которое говорит, что изменилось
   ```

   Claude спрашивает перед выполнением коммита. Прочитайте всю команду, затем выберите **Yes**. Если он также создаст ветку, это нормально: проверка работает на любой ветке. Чтобы сохранить коммит в текущей ветке, скажите об этом в своём запросе. Затем во втором терминале сохраните коммит для проверки и убедитесь, что ничего не осталось:

   ```bash
   git rev-parse HEAD > .practice/b-3-commit.txt
   git status
   ```

   `git status` заканчивается строкой `nothing to commit, working tree clean`.

## Ваша очередь

Повторите пример со вторым пробелом: ссылки, цель которых заключена в угловые скобки, например `[my notes](<my notes.md>)`.

1. Исследуйте в режиме плана: спросите, как приложение читает цель ссылки.
2. Спланируйте изменение с тестом в `test/links.test.js`. Отправьте план обратно, если он называет другие файлы, затем одобрите его с помощью **Yes, manually approve edits**.
3. Одобряйте правки и любые команды тестирования с помощью **Yes**, затем попросите Claude запустить тесты.
4. Просмотрите весь diff с помощью `/diff`, включая тестовый файл.
5. Попросите одно исправление, даже небольшое, и снова проверьте diff.
6. Когда исправление внесено, попросите Claude закоммитить изменение, его тест и ваше исправление вместе. Затем во втором терминале выполните `git rev-parse HEAD > .practice/b-3-commit.txt`.

В своём репозитории выберите небольшое собственное изменение, которое сопровождается тестом.

## Проверка

Вы закончили, когда все следующие условия истинны:

- [ ] Коммит, указанный в `.practice/b-3-commit.txt`, изменяет тестовый файл и как минимум один другой файл: `git show --stat $(cat .practice/b-3-commit.txt)`. **Windows:** `git show --stat (Get-Content .practice/b-3-commit.txt)`.
- [ ] Тесты проходят: `npm test` сообщает `fail 0`.
- [ ] Ничего не осталось незакоммиченным: `git status --porcelain` ничего не выводит.
- [ ] Самопроверка (не тестируется): вы прочитали весь diff перед коммитом и попросили Claude хотя бы одно исправление.

Во втором терминале выполните `npm run check -- b-3` в своей практической копии. В своём репозитории вместо этого выполните `npm run check -- b-3 --dir <your repo>` из практической копии. Если в этом репозитории нет скрипта `npm test`, сначала сохраните код выхода вашей тестовой команды с помощью `<your test command>; echo $? > .practice/b-3-tests.txt` (**Windows:** `<your test command>; $LASTEXITCODE > .practice/b-3-tests.txt`).

Если коммит не изменяет тестовый файл или изменяет только тесты, код и его тест не попали в один коммит: попросите Claude дополнить коммит недостающим тестом (`git commit --amend`) или объединить последние два коммита в один, если вы ещё не отправили их. Затем снова сохраните коммит с помощью `git rev-parse HEAD > .practice/b-3-commit.txt`. Если тесты не проходят, прочитайте первую ошибку и попросите Claude исправить код, а не тест. Если `git status --porcelain` перечисляет файлы, закоммитьте их или отложите с помощью `git stash push --include-untracked`.
